# 使用反馈闭环

## 分类与证据

- 用户只需描述问题、比较对象和希望保留的部分；执行者补齐记录，不要求用户填写表格。
- 区分本次要求、同类对象经验、全系列规则。未明确范围时先按本次处理，保留候选结论。
- 分别记录用户原话、实际观察、原因假设、验证结论。用户报告已收到不等于原因已证实。
- 证据绑定具体图片版本、参考图、技能提交和120px对照；优先使用可持久访问的文件路径或链接，不以临时路径作为唯一证据。
- 明确批准某一部分，只将该部分作为已确认参考。沉默、继续下一步或要求修复不等于整图批准。

## 执行顺序

1. 在案例记录登记反馈，先查相同对象或症状以避免重复；只存与设计相关的最小信息。完整复盘须同时检查需求/参考、逐轮图像、验收判定、交付与版本恢复、同步结果；分别标明已回看证据、历史记录和原因假设，不以最新一轮代替全程。
2. 获取原图与比较图，按 qa-120.md 固定条件对照。缺图时标记待证据，继续能完成的工作，不虚构诊断。
3. 写出“观察到的缺陷 → 原因假设 → 本次修改 → 保持项”，先修图，再检查目标与保持项；记录可观察成功条件。按delivery-review.md处理关键失败复核、两次无改善后的换方法及真实UI检查，不能只增加提示词。
4. 先取得修改后的实际对照和逐项结果，再更新规则；尺寸脚本通过、执行者预期或用户满意不能单独证明全局画风规则有效。将原因假设与实测发现分开，多个改动同时发生时不要声称单项因果已验证。本图改善只证明本案例有效。要提升为同类或全局规则，另用一种相关但不同的构图/材质案例检查是否引入退化；没有完成则保留候选状态。用户明确指定的新标准可直接生效，但效果标记未验证。
5. 更新最合适的规范段落或专项说明，合并重复规则，明确替代关系；禁止仅追加相互冲突的禁令。新规范的适用范围不得超过证据。
6. 在规则变更记录中关联案例、旧规则、新规则、验证范围及回退条件。经用户明确确认的成功图才升级为相应范围的正式参考。每次检查完成或收到确认后，按reference-library.md主动评估并提出入库建议；记录候选、建议入库、已入库或仅归档及理由，不能将建议写成已执行。入库与通用规则升级分别判定。
7. 校验链接、技能格式和相关规范一致性，核对GitHub与安装副本最新版本；保留无关改动，用预期提交保护分支更新，冲突时先合并。
8. 同步后回读内容或核对文件哈希。分别报告GitHub、当前安装副本的同步结果；失败保留本地改动并说明，不能把一端成功写成全部成功。其他设备未核实则不声称已更新。

## 复发反馈的核销

在同一张前后对照中分别核销目标与保持项：例如“细节减少”不能代替“奖励语义保留”，“层次增加”不能代替“活动氛围改善”。仅观察到中间变化时，最终目标仍记待验证。新反馈否定旧自评时，关联并更正该阶段状态，保留失败过程；同批多个图的联合修改不自动构成某条视觉经验的跨案例验证。五图实例及局部要求见feedback-records.md的F-20261020-001。

## 状态与回退

案例状态：待证据 → 待修改 → 待验证 → 本案例有效／未改善；用户确认单独记录。
规则状态：候选／生效／撤回；验证状态：未验证／局部验证／跨案例验证，分别记录。
如后续使用出现退化，关联新案例并缩小范围、修正规则或撤回；保留旧记录及提交，不抹去失败历史。
每次结束简报：本次图像结果、沉淀规则及范围、未验证项、同步结果。没有规则变更时如实说明。按delivery-review.md保留实际调用次数、首轮偏差、复发和退化；累计3个实际任务或同类问题复发时检查效果，不能用文档更新次数代替质量改善。
